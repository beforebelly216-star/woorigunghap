## 광고 선택의 이유를 만드는 구성

1. 기본 계산 결과를 먼저 온전히 제공한다. 궁합 점수·성향·세부 지표/근거를 광고로 가리지 않는다.
2. 계산 결과에 근거가 있는 질문을 고른다. 대화 차이, 강점을 쓰는 상황, 갈등 시 표현처럼 행동에 도움이 되는 추가 내용을 소개한다. 상대의 비밀/속마음·정확한 미래를 약속하지 않는다.
3. 추가 해설은 세 주제를 한 묶음으로 설명한다. 각 문단마다 광고를 반복해서 요구하지 않는다. 현재 예시 화면의 일반 문장은 개인화 결과로 사용하지 않는다.
4. 실제 연결 후 CTA는 ‘광고 보고 추가 해설 보기’로 시청 조건을 먼저 표시한다. 광고 길이를 임의로 보장하지 않는다. 기본 결과로 돌아가는 선택은 유지한다.
5. earned 확인→서버 권한/비용 한도→생성→저장 순서. 닫기만으로 보상을 지급하지 않는다. 저장된 결과 재열람/생성 실패 복구에는 추가 광고를 요구하지 않는 설계를 적용한다.
6. 실제 개인 결과의 질문 선택, 서버 보상 지급·저장·실패 복구는 아직 미구현이다. 준비 전 CTA를 활성화하지 않는다.

공식 광고 정책은 오해를 유도하는 구성, 의도치 않은 클릭, 정상 서비스 접근을 막는 구조, 같은 화면/같은 포맷 2개 이상, 클릭 보상·강제 refresh를 금지한다. 기본 무료로 유입한 뒤 기본 결과 자체를 숨기는 방식을 사용하지 않는다. 광고 전환율/완료율/저장 성공률/재열람/이탈을 함께 측정해 최적화해야 한다. 현재 측정 데이터와 광고 단가가 없으므로 수익/전환 상승은 확인하지 않았다.

## Claude 연결 — 확인된 현재 코드

- 기존 웹 `/api/compatibility/one-to-one` → `report-engine-v7` facade → 실제 `report-engine-v8` → `requestStructuredSegment` → Anthropic `/v1/messages`.
- 기본 모델은 `claude-sonnet-5`. `ANTHROPIC_NARRATIVE_MODEL`로 바뀔 수 있다. Haiku 4.5 값은 현재 resolver가 Sonnet 5로 치환하므로 환경변수만 바꿔 저렴한 Haiku로 전환할 수 없다.
- `REPORT_NARRATIVE_MODE=anthropic`, 서버 `ANTHROPIC_API_KEY` 필요. 키는 서버 요청 헤더에서 사용하며 미니앱 VITE 환경이나 JSX에 없다. 현재 로컬에는 `.env.example`만 있고 쉘 API 키도 없음. 배포 환경의 실제 키/모델/잔액과 현재 운영 성공 여부는 이 QA에서 확인하지 않았다.
- 사주·점수는 결정론 서버 계산. Claude는 그 근거로 문장을 쓴다. 일반 성향 해설을 심리 진단이나 상대 속마음의 사실로 취급할 수 없다.
- AI 입력의 구조화된 사람 정보는 원본 별칭/생년월일시 대신 일주·오행·계산 지표 등을 사용한다. 이름은 생성 후 서버 치환한다. 자유 질문은 알려진 이름·이메일·전화·날짜를 일부 정리하지만 다른 이름/주소/민감정보까지 완전 익명화를 보장하지 않는다. 광고용 신규 API에서는 자유 질문을 기본 제외하거나 별도 강화 검토가 필요하다.
- 기존 유료 endpoint는 계정/복구키 소유권과 결제 검증 후 생성한다. 광고 미니앱에서 현재 이 endpoint를 호출하지 않으며 CORS 허용 목록에도 없다. 결제 검증을 삭제해 무료로 열지 않는다. 별도 광고 생성 권한 모델이 필요하다.
- intro/dynamics/action 3개 묶음, 공백 제외 4,000~6,000자 목표. 최초 출력 상한 3,000/4,000/5,200토큰; truncation 재시도 상한 3,800/5,000/6,200토큰.
- 1회 시도 시간은 85/110/125초, 각 세그먼트 최대 2시도, 총 예산 상한 240초. 구조화 출력 400 응답 시 일반 JSON fallback 호출이 같은 시도 내 추가될 수 있으므로 ‘HTTP 요청이 정확히 최대 두 번’이라고 표현하면 안 된다.
- JSON schema/출력 길이/금지 표현/계산 근거 일치 품질 검사, 제한된 재시도 후 서버 근거로 결정론적 교정. 잘못된 해설의 무한 재시도 없음.
- DB `(payment_id, segment)` claim으로 중복 생성 보호, segment 저장 후 완료. 준비된 계산·저장된 해설을 재사용한다. 잠금 5분 만료/라우트 300초와 생성 예산의 여유는 실환경 부하에서 확인해야 한다.

광고 완료 1건 수익은 관측 eCPM/1,000으로 비교해야 한다. 배너/보상형의 실제 정산 단가·광고 채움률·완료율이 없어 수익이 비용을 덮는지 판단할 수 없다. 광고를 늘리기 전에 다음을 구현해야 한다.

1. 무료 기본은 결정론 계산과 계산 근거 문구로 제공 (AI 호출 불필요).
2. 광고 상세는 기존 긴 유료 리포트를 통째로 호출하지 않고, 세 주제의 짧은 한 묶음을 별도 스키마/프롬프트/상한으로 설계. 600~1,000 출력토큰은 실험 시작값이며 한국어 품질/길이를 검증해야 한다.
3. 계정별 일일 생성 수·전체 일일 비용 한도·서버 검증된 보상/일회성 grant·분석별 멱등 저장. 클라이언트 earned boolean만으로 권한 부여 금지.
4. 동일 결과 재열람은 저장 결과 사용. 생성 실패 시 보상 권한을 보존해 재시청 요구 없이 복구. 원본 입력을 공용 cache key나 공개 로그에 넣지 않는다.
5. usage 기반 실제 지출 측정. 현재 estimator는 Sonnet 단가 고정이고 cache 생성/읽기 요금을 합산하지 않는다. 모델 override/향후 caching 시 갱신 필요. 실패한 생성의 청구까지 포괄하는 영구 비용 원장은 현재 확인되지 않았다.
