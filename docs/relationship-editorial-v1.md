# 우리궁합 관계별 편집 계약 v1

기준: `relationship-editorial-v1`

## 공통 원칙
- 점수 계산은 기존 `romance / friend / coworker` 프로필을 유지한다.
- 짝사랑·썸·연인은 같은 romance 계산값을 사용하더라도 해석 전제와 행동 조언을 분리한다.
- AI는 서버 계산값만 설명하며 상대의 속마음, 관계 성립 여부, 미래 사건을 새로 만들지 않는다.
- 저장된 유료 리포트 JSON 스키마는 유지한다. 관계별 차이는 새 생성 시 편집 규칙과 UI 프레이밍에 적용한다.

## 짝사랑
전제: 아직 관계가 성립했다고 가정하지 않는다.

반드시 다룰 것: 접근 속도, 상대 반응 확인 기준, 부담 없는 연락·제안, 혼자 의미를 과해석하지 않는 기준.

금지: 이미 서로 좋아한다는 전제, 연인식 질투·소유권, 상대 호감 확정.

## 썸
전제: 상호 관심 가능성은 열려 있지만 교제와 독점성을 가정하지 않는다.

반드시 다룰 것: 연락 리듬, 호감 표현 균형, 관계 정의 대화, 한쪽만 속도가 빨라질 때의 조정.

금지: 공식 연인 전제, 배타적 관계 전제, 미래 약속 확정.

## 연인
전제: 이미 교제 중인 관계다.

반드시 다룰 것: 애정표현, 연락·데이트 리듬, 갈등 후 회복, 역할·주도권, 장기 관계 습관.

금지: 결혼 확정, 이별 예언, 상대 속마음 확정.

## 친구
전제: 우정 관계이며 연애적 끌림이나 독점성을 전제로 하지 않는다.

반드시 다룰 것: 연락 빈도, 약속 신뢰, 함께 하기 좋은 활동, 필요한 거리, 서운함을 푸는 방식.

금지: 연애 감정·성적 긴장·질투·결혼/이별 프레임.

## 직장동료
전제: 업무 관계다.

반드시 다룰 것: 업무 속도, 역할 분담, 보고·의사결정, 피드백, 업무 갈등 분리.

금지: 연애 문구, 사적 친밀감 중심 해석, 상사·동급·부하를 입력 없이 추정, 승진·이직 시기 예언.

현재 입력 계약에는 직장 위계가 없으므로 Drive 설계안의 상사/동급/부하 레이어는 후속 입력 확장 전까지 사용하지 않는다.

## UI 프레이밍
CH4·CH5·CH6·CH8의 제목과 도입 문구는 관계 유형별로 바꾼다. 본문 데이터 구조는 유지해 과거 구매 결과 재열람 호환성을 보존한다.
