# 우리사주 베타 전 프로모션·바이럴 UX 작업지침

> 목적: GPT/Claude가 동일한 GitHub `main`을 기준으로 단계별로 구현할 수 있는 실행 지침. 이 문서는 기능을 완료 처리하지 않으며, 실제 작업 순서는 `docs/NEXT_TASK.md`를 따른다.

## 1. 목표

유료 결과를 단순 열람으로 끝내지 않고 다음 루프를 만든다.

`결과 확인 → 공유 → 상대 반응 → Shared View → 신규 궁합 시작`

1:1과 1:N은 별도 시스템으로 분기하지 않고 공통 Share System을 사용하며, 데이터 표현만 다르게 렌더링한다.

## 2. 공통 원칙

- 공유의 주인공은 브랜드가 아니라 사용자의 관계 결과다.
- “공유해 주세요”보다 사용자가 자연스럽게 “이거 너 봐”라고 보내고 싶게 만든다.
- 억지 밈, 낡은 심리테스트 광고 문구, 과한 운명/속마음 단정을 피한다.
- 계산은 기존 서버 결정론 로직이 권위 데이터이며 AI는 계산 결과를 바꾸지 않는다.
- 이름/생년월일시 등 원본 개인정보를 새로 외부 AI에 전달하지 않는다.
- 공유 기능 때문에 유료 AI 재생성 또는 중복 비용이 발생하면 안 된다.
- Shared View는 전체 유료 리포트를 무료 공개하지 않고 공유 전용 데이터만 노출한다.

## 3. 공유 카드 제품 구조

### P0 카드

1. `Relationship Label`
   - 관계를 한 문장으로 캐릭터화.
   - 예: “잘 맞는데 꼭 한 번씩 서로 긁음”.
2. `Two Sides`
   - 잘 맞는 지점 1개 + 조율이 필요한 지점 1개.
3. `Send This`
   - 상대에게 직접 보내는 카드. 일부 결과는 teaser/blur 형태.

### P1 카드

4. `Receipt`
   - 관계 영수증 형태로 핵심 지표 여러 개를 짧게 정리.
5. `Recap`
   - 전체 관계 결과를 한 장으로 요약.

### 출력

- Instagram Story 우선 규격: 9:16, 1080×1920.
- 모바일 공유 시트, 이미지 저장, Kakao 공유를 고려한다.
- 카드 하나에 메시지 하나를 우선하고 정보 과밀을 피한다.

## 4. 1:1 / 1:N 공통화

### 1:1

- 대표 관계 한 줄
- 총점
- 가장 강한 관계 포인트
- 조율 포인트

### 1:N

- 단순 1등/꼴찌만 노출하지 않는다.
- 역할형 타이틀을 함께 사용한다.
  - 가장 편한 사람
  - 말이 잘 통하는 사람
  - 의외로 잘 맞는 사람
  - 나와 가장 다른 사람
- “최악”, “꼴찌”, “손절” 등을 기본 카드에 사용하지 않는다.

## 5. Relationship Copy 시스템

표현 톤은 세 가지를 기본으로 한다.

- `clean`: 짧고 관찰적인 표현
- `tease`: 상대에게 보내도 자연스러운 가벼운 놀림
- `curiosity`: 전체 결과를 보고 싶게 만드는 표현

기본 문법은 `관찰 + 작은 반전`을 우선한다.

예:

- 잘 맞는데 꼭 한 번씩 서로 긁음
- 편한데 가끔 이상하게 경쟁함
- 서로 다른데 중요한 순간엔 비슷함
- 말은 잘 통하는데 양보는 느림

다음 계열 표현은 기본 브랜드 카피에서 피한다.

- 전생에 나라를 구한
- 환상의 콤비 / 찰떡궁합
- 실화냐 / 팩폭 / 소름 / 대박
- 상대방의 숨겨진 속마음
- 운명의 상대 / 악연

## 6. 관계 유형별 해석 레이어

같은 계산값도 관계 유형에 따라 사용자가 실제 궁금해하는 맥락으로 번역한다.

### 짝사랑

핵심: 가능성 / 거리 / 타이밍

### 썸

핵심: 긴장감 / 속도 / 확신

### 연인

핵심: 안정 / 반복 갈등 / 지속성

### 친구

핵심: 편안함 / 재미 / 거리감

### 직장동료

핵심: 협업 / 속도 / 역할 / 피드백

관계별 TEASE 강도는 친구 > 연인 > 썸 > 직장동료 > 짝사랑 순으로 보수적으로 적용한다.

## 7. 카피 생산 매트릭스

패턴 6종:

- 안정형
- 티키타카형
- 반전형
- 거리조절형
- 노력형
- 극과극형

`5개 관계 유형 × 6개 패턴 = 30개 셀`

각 셀에서 최소:

- clean 4개
- tease 2개
- curiosity 2개

총 raw 약 240개를 생성하고, 중복·범용성·오글거림을 검수하여 120~160개를 프로덕션 후보로 남긴다.

### 카피 평가 기준

각 문구를 5점 척도로 검수한다.

- 실제 공유 가능성 >= 4
- 자연스러움 >= 4
- 관계 유형 특이성 >= 3
- 계산 결과 반영도 >= 4
- 호기심 >= 3
- 오글거림 위험 <= 2

## 8. Shared View

공유 링크 진입자는 기존 전체 결과 페이지가 아니라 별도 Shared View를 본다.

기본 구조:

1. “OO랑 당신은 이런 조합이래요.”
2. 대표 관계 한 줄
3. 제한된 핵심 결과
4. 반응 질문
   - 꽤 맞음
   - 반반
   - 아닌데
5. 반응 후 신규 궁합 CTA

Shared View는 비로그인 상태에서도 안전하게 열리되 전체 유료 리포트나 원본 입력정보를 노출하지 않는다.

## 9. Analytics 최소 이벤트

- `share_card_open`
- `share_style_selected`
- `share_image_download`
- `share_kakao_click`
- `shared_view_open`
- `shared_view_reaction`
- `shared_view_cta_click`
- `shared_view_new_report_start`

핵심 지표:

- Share Rate
- 공유 1건당 Shared View 유입
- Shared View → 신규 궁합 시작 전환율

## 10. 개인정보 / 유료콘텐츠 원칙

- 공유 카드에 생년월일시를 표시하지 않는다.
- 원본 사주 입력값을 공유 URL에 포함하지 않는다.
- 이름은 결과에서 사용하는 표시명 수준만 사용한다.
- Shared View에서 전체 유료 리포트를 공개하지 않는다.
- 공유 URL은 추측하기 어려운 token 기반 구조를 우선한다.
- 기존 소유권/결제 검증을 우회하지 않는다.

## 11. 단계별 실행 계획

### Phase P1 — 정보구조/계약 확정

작업:

- 기존 결과/보관함 데이터 구조 확인
- Share 전용 데이터 DTO 정의
- 1:1/1:N 공통 필드와 분기 필드 정의
- Shared View 공개 범위 정의
- privacy/payment ownership 경계 확인

완료 기준:

- 기존 계산/결제/AI 계약을 변경하지 않고 Share System 입력 계약이 문서/타입으로 명확함
- 1:1과 1:N 모두 같은 상위 Share 모델로 표현 가능

검증:

- 관련 타입/계약 테스트
- `npm run lint`
- `npm run build`

### Phase P2 — 카피 라이브러리 구축

작업:

- 30셀 × 최소 8개 raw copy 생성
- 약 240개 후보 확보
- 중복/범용/오글거림 검수
- 120~160개 프로덕션 후보 선정
- `relationshipType × pattern × tone` 데이터 구조 정의

완료 기준:

- 짝사랑/썸/연인/친구/직장동료 모두 독립적인 언어를 가짐
- 낮은 점수도 공유 가능한 카피 존재
- 금지/지양 표현이 기본 라이브러리에 없음

검증:

- 중복 검사
- 관계별 샘플 snapshot/contract test 가능 시 추가
- `npm run lint`
- `npm run build`

### Phase P3 — P0 공유 카드 UI

작업:

- Relationship Label
- Two Sides
- Send This
- 9:16 이미지 렌더링/저장
- 모바일 결과 페이지 진입점

완료 기준:

- 1:1과 1:N 모두 3개 카드 생성 가능
- 360/390/430px에서 카드 선택 UI 깨짐 없음
- 긴 표시명/낮은 점수/높은 점수에서도 레이아웃 유지

검증:

- 모바일 실기기/브라우저 확인
- 이미지 저장 확인
- `npm run lint`
- `npm run build`

### Phase P4 — Kakao 공유 + Shared View

작업:

- Kakao 커스텀 공유 메시지
- 공유 token/URL
- Shared View
- 신규 궁합 CTA

완료 기준:

- 공유자가 전체 유료 리포트를 노출하지 않고 제한 정보만 공유 가능
- 비로그인 수신자도 Shared View 진입 가능
- CTA에서 정상적으로 신규 입력 플로우로 이동

검증:

- 실제 Kakao 공유 E2E
- 비로그인/로그인 Shared View
- 권한/토큰 회귀 테스트
- `npm run lint`
- `npm run build`

### Phase P5 — 반응 UX + Analytics

작업:

- 꽤 맞음 / 반반 / 아닌데
- 반응 후 CTA
- 최소 analytics 이벤트 연결

완료 기준:

- 반응이 유료 결과를 변경하지 않음
- 모든 핵심 공유 퍼널 이벤트 수집 가능
- 이벤트 실패가 결과 열람을 막지 않음

검증:

- 이벤트 payload 확인
- Shared View 회귀 테스트
- `npm run lint`
- `npm run build`

### Phase P6 — P1 카드 확장/실험

작업:

- Receipt
- Recap
- 카드/카피 A/B 테스트 기반 준비

완료 기준:

- 기존 P0 Share System을 재작성하지 않고 플러그인형 확장 가능
- 실제 운영 데이터 기반으로 우선순위 판단 가능

## 12. GPT / Claude 작업 규칙

각 단계 시작 전 반드시 최신 `main`을 다시 확인하고 아래 순서로 읽는다.

1. `AGENTS.md`
2. `docs/PROJECT_STATE.md`
3. `docs/NEXT_TASK.md`
4. `docs/DECISIONS.md`
5. 이 문서

운영 blocker/hotfix가 있으면 본 프로모션 작업보다 우선한다.

한 번의 작업에서는 한 Phase 또는 그보다 작은 단위만 수행한다. unrelated refactor를 하지 않는다.

작업 완료 후 `PROJECT_STATE`, `NEXT_TASK`, `Current HANDOFF`를 실제 상태에 맞게 갱신한다.
