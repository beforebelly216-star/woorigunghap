2026-10-03 사용자 결정. 이전 미니앱 광고 전용 결정을 대체한다. 이 문서는 출시 구현 완료 선언이 아니다.

## 네트워크 권한 연결 — 2026-10-05

별도 토스 계정/공개 동의 네트워크와 쌍별 무료 결과 API·화면을 구현했다. 내부 스냅샷은 정렬된 두 참여자의 입력 버전으로 구성하며 추가 참여로 기존 키가 바뀌지 않는다. 항목 사용/Claude에 연결하기 전 완료 시 재권한 확인·비용/보관/환불 설계가 필요하다. 기본 OFF/실기기 미검증. `TOSS_NETWORK_IMPLEMENTATION.md` 참조.

## 서버 기반 구현 상태 (후속 배치)

- `fullbuy-store-core.ts`: Postgres 영구 원장, IAP/광고 출처 분리, 전역 지급 참조 중복 방지, 개인별 항목 예약/완료/반환, 동일 항목 최대 2회 시도. 계정 행 잠금과 한 트랜잭션으로 잔액 검사·예약·원장을 묶는다. 지급 함수는 서버 내부이며 외부 지급 endpoint는 없다.
- `fullbuy-chapter-service.ts`: 서버에서 권한을 확인한 스냅샷만 받는 내부 생성 어댑터. 예약을 얻은 작업 하나만 생성, 120초 제한/AbortSignal, 품질 검증 뒤 저장·사용 확정. 실패는 출처별 반환, 늦은 작업은 attempt_id로 차단. 실제 Claude 호출과 계산 근거 품질 검사·네트워크 계정/동의 검증은 아직 연결하지 않았다.
- 중단된 예약은 10분 뒤 서버에서 반환한다. 지갑 조회 또는 다음 내부 생성 요청이 복구를 실행한다. 10분보다 오래된 작업은 반환 후 결과를 저장할 수 없다. 주기적 cleanup/실제 다중 서버 부하 검증은 후속 작업이다.
- `GET /api/toss/wallet`: 정확한 Origin·토스 Bearer 계정 확인, 개인 지갑만 조회/오래된 예약 복구. `APPS_IN_TOSS_FULLBUY_ENABLED=false` 기본 OFF, no-store, DB 요청 20초 제한. 실제 프런트 지갑 표시는 아직 미연결이다.
- 주문 조회의 공식 공개 응답은 orderId/sku/status를 제공하지만 구매자 식별자는 없다. `x-toss-user-key`가 이 API에서 구매자 필터를 보장하는지는 공식 문서/실기기로 확인하지 못했다. 기존 상태 route는 `verificationScope:payment_status_only`, `productGranted:false`를 반환한다. 이 상태 조회만으로 유료 지급을 연결하지 않는다. 출처: https://developers-apps-in-toss.toss.im/api/iap
- 주문별 유료 지급 참조와 예약별 유료/광고 출처는 기록한다. **주문별 사용량 배분(환불 재화 회수), 계정 탈퇴·결과 보관 정책, 권한 검증, IAP 주문 소유권, 보상형 서버 검증**은 활성화 전 필수 남은 작업이다. 사용자 ID는 내부 식별자이며 새 원장에는 생년정보·토스 userKey·실명·비밀값을 기록하지 않는다.
- PGlite(개발 의존성)의 실제 PostgreSQL 엔진에서 운영과 같은 SQL을 실행했다. 중복/다른 계정 지급 참조, 잔액 부족, 같은/다른 항목 동시 요청, 보상 우선 예약/출처 반환, 늦은 작업, 재열람 보존, 2회 제한, SQL 중도 오류 rollback, stale 반환, 생성 중복/품질 실패/제공자 실패 검증 PASS. 단일 연결의 큐 동시성 검증이며 실제 Neon 다중 세션 부하/운영 DB 검증은 아니다.
- 재현: `npm run test:fullbuy`. Windows sandbox의 tsx 사용자 조회 오류 시 제한 밖에서 `node --import tsx scripts/fullbuy-store-test.ts`로 검증했다. 운영 DB/Claude/실제 결제 접속 없음.
## 확정된 이용 단위

- 기본 관계망과 1:1 계산 결과는 무료다. 점수·근거를 본 뒤 원하는 상세 항목을 고른다.
- **보상형 광고 완료 1회 → 풀매수 3개 지급. 상세 항목 하나 → 3개 사용.** 세 항목 전부는 9개다.
- 풀매수는 현금·토스 포인트·투자상품이 아닌 앱 내 상세 해설 이용권이다. 양도/환전하지 않는다.
- 이미 열어 저장한 같은 결과 버전의 같은 항목은 다시 차감하지 않는다. 다른 항목은 별도 3개다.
- 광고와 구매가 같은 개인 지갑으로 들어오되, 서버 원장에서는 지급 출처·구매 주문·잔여분을 구분한다.
- 구매 수량/가격/환불·보관 기간은 아직 확정하지 않았다. UI의 광고·구매·실제 차감은 비활성이다.

## 화면 및 전환

1. 홈: 친구 네트워크 진입/미리보기, 두 사람 궁합도 유지한다.
2. 네트워크 초대: 토스 공식 미니앱 링크로 참여. 각자 자기 정보를 입력하고 그룹 내 관계 공개에 동의한다. URL에는 생년정보를 넣지 않는다.
3. 네트워크 결과: 전체 쌍/내 관계 필터. 각 쌍을 누르면 해당 두 사람의 무료 1:1 기본 결과로 간다. 4명=6쌍, 12명=66쌍. 관계 점수와 예고 문구는 실제 계산 근거만 사용한다.
4. 1:1 상세: 무료 결과 → 풀매수 보유량 → 대화/강점/갈등의 항목별 3개 버튼. 공포·불운·상대 속마음 단정·가짜 긴급성을 사용하지 않는다.
5. 잔액 충분: 제목·3개 사용·남을 수량을 확인하고 요청한다. 성공 후 보관함에 저장한다.
6. 잔액 부족: 부족 수량, 광고 완료 시 3개, 구매 상품의 실제 가격·수량을 같은 충전 패널에 표시한다. 광고 실패/취소 시 기본 결과로 돌아갈 수 있다. 반복 자동 재생하지 않는다.
7. 구매 후: 지갑을 갱신하고 원래 고른 항목으로 돌아간다. **구매가 자동으로 항목 사용 동의가 되지는 않는다.** 별도 사용 확인 후 해설을 연다.
8. 저장된 해설 → 다른 관계 탐색/새 친구 초대. 지갑은 개인 단위이며 한 참여자의 사용이 다른 참여자에게 이용권을 지급하지 않는다.

현재 `/network-preview`는 가상 별명 4명의 모든 6쌍을 제공한다. `/result-preview`는 항목별 사용 확인/문장 예시를 보여준다. 로그인·실제 분석·초대·서버 지갑은 아직 연결 전이다.

## 소모성 상품 제안 (미확정)

| 제안 상품명 | 풀매수 | 사용할 상세 항목 수 | 용도 |
|---|---:|---:|---|
| 풀매수 3개 · 상세 해설 1항목 | 3 | 1 | 한 가지 궁금증 |
| 풀매수 9개 · 상세 해설 3항목 | 9 | 3 | 한 관계의 세 항목 |
| 풀매수 30개 · 상세 해설 10항목 | 30 | 10 | 여러 관계 탐색 |

초기에는 3개/9개만 등록하고 30개는 실제 재구매·원가를 본 뒤 추가하는 것을 권장한다. 할인·무료체험·구독은 초기 범위에서 제외한다. 특정 SKU가 9개라고 클라이언트가 주장해도 서버가 콘솔 SKU 허용목록으로 수량을 정한다.

가격은 실제 Claude 항목당 비용, 실패/복구 비용, 저장 비용, 결제 수수료, 광고 수익을 측정한 뒤 확정한다. 공식 가이드 현재 안내는 앱마켓 15%(매출에 따라 변동 가능)+토스 5%다. 세금·정산 기준을 확인하기 전 판매가의 80%를 순이익으로 단정하지 않는다. 핵심 지표는 광고 횟수뿐 아니라 **항목당 공헌이익, 미지급 주문, 차감 후 실패, 구매 전환율, 초대 참여율**이다.

## 공식 가이드에 따른 구현 순서

출처: https://developers-apps-in-toss.toss.im/guide/monetization/in-app-payment (2026-10-03 확인).

1. 콘솔 사업자·정산 정보 검토 완료 → 소모품 상품 등록. 상품 이미지 1024×1024, 상품명에 수량/용도를 명시한다. 공급가 400~1,400,000원, 10원 단위이며 VAT가 더해진 판매가를 사용자에게 표시한다.
2. 로그인/mTLS 서버 연결. 비밀 인증서와 userKey는 클라이언트에서 전달받아 신뢰하지 않는다. 인증서/키를 채팅·Git에 넣지 않는다.
3. `IAP.getProductItemList`의 SKU·가격·상품명을 표시한다. 실제 가격 대신 코드에 고정한 예시 가격으로 구매를 받지 않는다.
4. `IAP.createOneTimePurchaseOrder` + `processProductGrant`: 서버가 인증된 구매자의 주문 ID/실제 주문 상태/SKU를 조회 검증한다.
5. DB 트랜잭션으로 주문 UNIQUE 기록·풀매수 지급·원장을 함께 저장한다. 이미 지급된 주문은 같은 성공을 반환하고 다시 지급하지 않는다. **영구 저장이 성공했을 때만 콜백 true.** 상태 검증만 통과한 것은 지급 완료가 아니다.
6. 앱 시작/충전 진입 시 `IAP.getPendingOrders` → 동일 서버 지급 → 성공한 주문만 `IAP.completeProductGrant`. 서버 실패면 미결 상태를 남기고 복구 UI를 제공한다.
7. `IAP.getCompletedOrRefundedOrders`와 서버 최신 주문 조회로 환불 이력/상태를 재확인한다. iOS는 Apple이 환불을 판단하며 Android는 토스 요청/파트너 검토/Google 최종 판단을 따른다. 주문별 남은 유료 재화·사용 기록을 보존하고, 환불된 주문을 복구 과정에서 재지급하지 않는다. 이미 사용된 재화의 환불 처리·콘텐츠 권한은 정책 확정 후 구현한다.
8. 샌드박스 Android/iOS에서 결제/취소/지급 실패/앱 종료/재진입/동시 탭/중복 콜백/환불을 확인한 후 활성화한다.

## 현재 코드와 실제 필요한 변경

- `apps/toss/src/iap-client.js`: 동시 구매 방지·지급 중복 병합·미결 주문 복구 어댑터가 있다. 상품 목록/충전 화면/영구 지갑 연결은 없다.
- `src/app/api/toss/iap/status/route.ts`: 인증된 토스 계정과 주문/SKU/상태를 확인하지만 **productGranted:false**, 영구 지급 없음. 기존 단일 SKU 설정을 풀매수 SKU 허용목록으로 확장할 필요가 있다.
- 서버에 지갑, 지급 출처별 원장, 주문 지급, 항목 권한, 생성 작업을 추가한다. 제안 endpoint: `/api/toss/wallet`, `/api/toss/iap/grant`, `/api/toss/chapters/unlock`; 현재 생성·운영되는 API가 아니다.
- 기존 웹 PortOne 결제/저장 결과는 별도 유지한다. 새 토스 아이템을 기존 결제 ID나 이름으로 자동 병합하지 않는다.

### 사용·생성·실패의 원자성

서버가 계정/그룹 참여 권한/공개 동의/잔액을 확인 → 동일 항목 권한 조회 → 3개 예약과 작업 생성 → 단일 작업만 AI 실행 → 품질 통과 해설 영구 저장과 예약 확정 → 권한 반환.

동시 두 요청은 잔액을 중복 사용하거나 AI를 중복 호출하지 않는다. 실패 시 예약을 돌려주고 실패 이력을 기록한다. 대기 중 새로고침은 같은 작업을 조회한다. 무한 자동 재시도하지 않는다. 이미 저장한 해설을 새 AI 출력으로 덮어쓰지 않는다. 공유 그룹의 모든 쌍을 미리 AI 생성하지 않고 **요청된 항목만** 생성한다.

### 네트워크 권한·보관

기존 네트워크는 모든 쌍의 결정론 점수와 선택 UI를 제공한다. 공개 DTO에는 생년정보가 없고 서버에서는 암호화 저장한다. 기존 네트워크 보관은 30일이므로, 아이템으로 연 상세가 함께 사라지지 않도록 **별도 보관함·삭제/탈퇴/환불 정책을 구현한 뒤** 유료 기능을 켠다. 무기한 보관을 약속하지 않는다.

모든 참여자가 다른 참여자끼리의 상세까지 볼 수 있게 하려면, 실제 로그인 계정과 참여자를 서버에서 연결하고 그 공개 범위에 명시적으로 동의해야 한다. 기존 초대 토큰을 소유했다는 이유만으로 새 상세 권한을 부여하지 않는다.

권한/캐시 기준은 그룹 ID + 정렬된 두 참여자 ID + 해당 둘의 입력 버전 + 관계 유형 + 계산/서술 버전 + 항목 ID다. 제3의 친구가 들어와 전체 graphVersion이 바뀌어도 기존 두 사람의 권한을 초기화하지 않는다. A/B 순서만 바뀐 같은 쌍은 재차감하지 않는다. 다른 계정은 각자 권한을 얻으며 콘텐츠 재사용 캐시는 접근 권한 검사 뒤에만 사용한다.

## 광고 출시 조건

현재 배너 1개와 전면형 2개만 등록되어 있다. **전면형 ID를 보상형으로 간주하지 않는다.** 별도 보상형 ID로 `userEarnedReward`를 처리한다. 단순 `dismissed`/클릭/로드 성공은 지급 조건이 아니다. 광고 지급의 재전송 방지와 서버 검증/공식 검증 수단 지원 여부를 확인해야 한다. 클라이언트 이벤트만 보고 무제한 서버 지갑을 충전하는 구조로 출시하지 않는다.
